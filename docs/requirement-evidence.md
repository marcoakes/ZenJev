## Evidence boundaries

- Product code is in the separate ZenJev repository. The unchanged Wringer harness performs standalone `trusted_local` verification through [.wringer.yaml](../.wringer.yaml) and [scripts/verify.mjs](../scripts/verify.mjs). This is not a contained ACP run or a demonstrated red-first workflow. See [execution decision](execution-decision.md) and [implementation decisions](decisions.md).
- Native PostgreSQL startup was blocked by this environment's shared-memory restrictions. The portable runtime uses PGlite's PostgreSQL WASM engine through its local wire-protocol server. Persistence, SQL constraints, state transitions, and scheduled race scenarios can be exercised there. **Native PostgreSQL multi-session concurrency, native crash recovery, and production load behavior remain unverified.** A suite named “PostgreSQL persisted workflows” does not change which engine actually ran it.
- Jev, Zendesk, and application GitHub HTTP tests use intercepted requests and synthetic responses. No live Jev inference, Zendesk ingestion/write, or application GitHub write has been verified. The existing-helper GitHub identity check is a separate preflight observation, recorded in [credentials](credentials.md).
- Review performed by Codex and its subagents is **delegated agent review**. It is not Marc's personal usability verdict, signature, or proof of human presence. No owner's approval event was manufactured. No repository creation, push, pull request, publication, visibility change, or deployment is established by this map.
- Database suites require the isolated `zenjev_test` database. The conditional backend suite can skip if `TEST_DATABASE_URL` is absent; orchestration tests require a valid isolated database. Skips cannot satisfy a persistence requirement. Browser tests require the actual application and worker. Report the prerequisites and actual outcomes rather than counting source definitions as executed cases.

## Additional implemented controls and focused checks

- Configurable team ownership criteria, fixed team allowlist, and initial unvalidated routing/engineering/missing-information/multiple-issue/match cutoffs are editable by administrators. Provider tests `sends configured team descriptions with a fixed option allowlist and saved cutoffs` and `rejects nonfinite/out-of-range policy and unknown team keys before HTTP`, plus backend `configurable policy is persisted and frozen into decisions`, cover their boundaries. Saved decisions carry policy provenance; the threshold simulator reads frozen predictions.
- Append-only audit is enforced by a database trigger. Backend `audit records are append-only at the database layer` attempts UPDATE and DELETE and verifies rejection plus unchanged data. The SQL test runs on the engine named by the final report.
- Privacy retention is count-only by default with explicit apply. Backend `retention CLI dry-run and apply remove only selected old records and preserve audit` invokes the actual CLI, checks selection, deleted ticket/comment records, retained normal fixtures, and a preserved audit trail.
- External identifiers are preserved without JavaScript integer rounding. Provider `preserves external numeric identifiers beyond JavaScript safe integer precision` covers this parsing boundary.
- Provider reads use bounded retries and recorded scheduling metadata. Provider `honours Retry-After and bounded retry count` and `classifies GitHub exhausted-rate 403 as retryable and preserves the server deadline` assert retry count/deadlines. Mutations take the separate uncertain-outcome path.
- Keychain observations remain the narrow metadata/helper checks in [credentials](credentials.md). The application does not resolve build credentials from Keychain. Current canary tests cover launcher environment isolation, text redaction, and provider error sanitisation; **a dedicated stubbed macOS Keychain-lookup/redaction regression test is not present in these product suites**. Do not rename the launcher test as one.
- The approved artwork is an unchanged design asset, not a screenshot of the application. Browser screenshots are produced from the running app under the paths recorded by the test report; the browser suite defines desktop queue/detail/engineering/evaluation and narrow queue/detail captures.

## Final report and handoff obligations

The [test report](test-report.md) records observed commands/results, runtime limits, failures and repairs, screenshots, blocked browser trace, and delegated review. It still requires the final committed candidate identity and source-bound Wringer result. Successful application tests and the production build do not erase the blocked browser gate or supply unavailable live Jev evaluation.

Remaining external verification is explicit: native PostgreSQL concurrency/recovery; real Jev/GitHub/Zendesk requests and authorised mutations; deployment-specific authentication/network/privacy behavior; an owner-provided personal usability verdict; and any separately authorised publication. None of those is supplied by a passing fixture test, a local approval receipt, or this map. Reproducible startup and review steps are in the [README](../README.md) and [demo script](demo-script.md).
